# 読まれる記事の構成・文章術(リビング文書 / 軽量ホットセット)

> このファイルは書き手(note-writing)が見る **洗練された最低限の原則(ホットセット)** に保つ。
> **細かい文章テクニックは持たない** — それは note-editor(`skills/note-editor/references/editor-rubric.md`)に集約し、
> 執筆後のレビューループで底上げする。ここに足すのは、note-editor の指摘が頻発して**昇格**したものだけ。
> 効かなくなった原則は note-editor 側へ**降格**(削除しない)、重複は**蒸留**して短くする。いずれも提案→承認で適用。
> **書き手の声・個性(敬体・一人称・温度・避ける言い回し・時制スタンス)はここに持たず `personas/<名前>.yaml` へ。** 仕組みは references/personas.md。
> 最終更新: 2026-06-04(persona 分離)。

技術・開発系の note 記事を想定。読者は「自分の課題が解けるか」を数秒で判断して離脱する前提で設計する。

## 1. 掴み(導入)

- 冒頭2〜3文で「**誰の・どんな課題を・どう解決する記事か**」を言い切る。前置き・自己紹介から入らない。
- 「この記事を読むと何ができるようになるか」を導入で約束する。
- 結論や成果(動いた図・数値・before/after)を先に見せると続きが読まれる。
- ※掴みの癖(あるある自己同定・温度の出し方)は **persona**(`personas/<名前>.yaml`)に置く。

## 2. 構成(骨子)

- **結論先出し**。理由・手順・詳細は後。技術記事の読者は答えから読みたい。
- 見出し(H2/H3)を上から並べただけで記事の筋が通るかを点検する。通らなければ構成がまだ甘い。
- 1セクション=1論点。話が混ざったら見出しを分ける。
- 定番の型(出発点。記事ごとに崩してよい):
  - **How-to / 手順**: 課題 → 結論(完成形) → 前提 → 手順 → つまずきと対処 → まとめ
  - **考察 / 解説**: 問い → 主張 → 根拠(データ・式・例) → 反論への配慮 → 結論
  - **ツール紹介**: 何が嬉しいか → 使い方(最短) → 実例 → 向き不向き → まとめ

## 3. 段落・文

- 一段落は短く(画面で2〜4行)。スマホで読まれる前提。
- 一文一義。接続を多用して長くしない。
- 抽象を書いたら直後に**具体例・コード・数値**で着地させる。具体が無い段落は薄い。
- 専門用語は初出で一言補う。ただし読者の前提知識に合わせ、説明過多にもしない。
- ※文体・声(宣言しない/AIっぽさ回避/時制スタンス/敬体/一人称)は **persona**(`personas/<名前>.yaml`)に置く。判定の詳細は note-editor の editor-rubric.md(`ai-generic`)。

## 4. 図・コード

- 図は「文章だと伝わりにくい構造・関係・流れ」に絞って入れる(装飾目的の図は省く)。
- 図を入れる時は **何を一目で伝えるか(intent)** を先に決めてから図メタを書く。
- **図はどんどん入れてよい。ただし1セクション=言いたいこと1つなので、基本は1セクション1図で足りる**。
  1つの節に複数の図が要るなら、節の範囲が広すぎる兆候=見出しを分けるサイン。
- **図中に技術名・固有名詞(ツール名)が出るなら、それと分かるアイコンを指定する**(無地ラベルは識別しづらい)。
  詳しいプロンプト規約は references/image-styles.md。
- コードは動く最小単位を見せる。長い全文より、要点に絞った抜粋+説明(コード/設定は図にせずコードブロックで)。

## 5. 締め

- 末尾で「**読者の次の行動**」を示す(試す手順・関連リンク・次に読むもの)。
- 学びを1〜3行で要約。記事の約束(導入)を回収できているか確認。

## 6. 有料記事の構成(売る場合)

有料記事は「無料部分=購入判断の材料」「有料ライン=最も知りたい所の直前」で設計する。仕組みは note-spec.md 参照。

- **無料部分で売る**: 無料で読める範囲だけで「課題・結論の方向・この先に何があるか」を伝え切る。
  無料部分が薄いと買われない。逆に答えを全部無料で書くと買う理由が消える。
- **有料ラインの位置**: 興味が最大化した瞬間(問題提起しきった所 / 「で、具体的な手順は?」の直前 /
  結論は見せたが再現方法はこれから、という所)に引く。途中で唐突に切らない。
- **有料部分の中身**: 再現可能な具体(手順・コード・数値・設定・実データ)。無料部分の約束を必ず回収する。
- **価格と分量の釣り合い**: 価格に見合う具体性があるか。薄い内容を高値にしない(信頼を損なう)。
- 技術記事では「考え方・背景は無料、動かすための具体一式は有料」が収まりやすい型。

## 7. タイトル(本文の外だが効く)

- 具体性 > 煽り。「何が得られるか」が分かる語を入れる。数値・固有名詞は強い。
- 中身と乖離させない(クリック後の離脱・信頼低下を招く)。
