# note-editor 詳細ルブリック(観点11 + category キー + severity)

このファイルは editor の本体ルブリック。レビュー時に読み込む。**機能する枠組み(普遍)だけを置く配布物**で、
リビング扱い(昇格/降格/蒸留)はしない。観点11の見出し・severity 目安・category キー・「修正前/修正後/意図」
の出力形式は固定。
**書き手の好み・癖の判定(避ける言い回し・時制・気取り・温度・画像審美・観点ごとの嫌う型 等)はここに持たず、
対象記事の `persona`(`personas/<名前>.yaml`)の `編集観点` / `避ける言い回し` / `画像審美` を源泉とする**。
persona が無色(空)なら editor は機構だけで動く。

改善ループの向け先は **persona / style**(SKILL.md の「persona/style への反映提案」を参照)。
このファイル自体の改修は、**書き手や記事ジャンルが変わっても効く**普遍と確信できる場合のみ、ユーザー承認で行う。

## 矛盾時の判定(優先順位)

ルールが衝突したとき、editor は以下の順で判定する。**上が下を上書きする**:

1. **絶対固定**(persona でも上書き不可) — note.com の仕様(`note-spec.md`)・本ファイルの機構部分
   (severity / category / 「修正前/修正後/意図」の出力形式・観点11の枠組み)・SKILL.md のワークフロー骨格。
2. **対象記事の persona / 該当 styles** — `避ける言い回し` / `編集観点` / `画像審美` / `温度・距離` 等。
   **本ファイルの観点細目(下記 §1〜§11)と矛盾したら persona が勝つ**(書き手の意思が上)。
3. **本ファイルの観点細目** — 機能する判定(主述対応・指示語の曖昧さ 等)。persona が無色(空)ならここだけで動く。

例: persona に「段落は長めでよい」とあれば、§6 スマホの「段落短く」では指摘しない。
   persona に「タイトル末尾の(補足)は許容」とあれば、§3 タイトルでは指摘しない。
   persona に「インラインコード使いたい」とあっても、§11 公開前の `spec-violation` は出す(絶対固定)。

詳細は `docs/SPEC.md` §3「優先順位(矛盾したとき何が勝つか)」。

## category キー一覧(findings の集計キー。新規は慎重に追加)

## severity 目安

- **重大**: 読まれない/約束破り/構造破綻。芯が不明・1記事多テーマ・タイトルや冒頭で読む理由が立たない・
  読後に何も残らない・タイトルと本文の約束がズレる、等。
- **中**: 読みを弱める。見出しが弱い・段落や文が長い・文体が単調/AIっぽい・note 仕様違反・まとめが弱い・
  太字/箇条書き/画像にすべき箇所が放置、等。
- **軽**: nit。表記ゆれ・細かい言い回し・指示語の軽い曖昧さ、等。

note-writing ループでは**重大・中を修正対象**にし、軽は報告のみ。

---

## 1. 記事の芯  (重大寄り)

- この記事は一言で何を言っているか。1記事1テーマか。話題が複数なら記事を分けるべきでないか。
- 読後に読者へ何が残るか。筆者が本当に言いたいことが途中で埋もれていないか。
- 問題があれば、記事の中心を**一文で言い直す**。

## 2. 想定読者  (重大寄り)

- 誰に向けた記事か。前提知識はどの程度か。読者はなぜ読むのか。
- 冒頭で「自分に関係ある」と思えるか。疑問に答える順番になっているか。
- **冒頭で約束した『なぜ』は、対応する手順より前に置く**。設計判断や売りを宣言したのに、その理由を作業手順の後ろや末尾に回すと、読者は理由抜きで手順を読まされる（`answer-order` / `point-buried`）。「理由は後述」の連打もこの粗。
- 想定読者が曖昧なら、候補を2〜3パターン出す。

## 3. タイトル  (重大寄り)

note ではタイトルが最重要。短ければよいわけではない。

- 誰が・何をして・どうなったかが分かるか。オチを隠しすぎていないか。抽象的すぎないか。
- 具体的な属性・数字・状況・変化が入っているか。読者が本文を読む理由を想像できるか。
- 釣りすぎて本文との約束がズレていないか。
- 嫌う定型・蛇足は **persona の `編集観点.タイトル`** を見て判断する(無色なら指摘しない)。
- 案を出すときは**方向性を分ける**: 結論型 / 体験型 / 悩み寄せ型 / 違和感・発見型 / 少し長いが分かる型。

## 4. 冒頭リード  (重大寄り)

冒頭で読者は読むかを決める。

- 最初の3〜5行で何の記事か分かるか。なぜ今これを書くのかがあるか。
- 前置きが長すぎないか。
- 嫌う始め方(無難な一般論から入る 等)は **persona の `編集観点.冒頭`** を見て判断する(無色なら指摘しない)。
  必要なら改善案を複数(方向性別に)。

## 5. 見出し構成  (中)

見出しだけで流れが分かる状態を目指す。

- 見出しだけで要点が追えるか。抽象的すぎないか。順番に違和感がないか。
- 読みたい箇所を見つけやすいか。目次にして意味が通るか。章ごとの役割が明確か。
- 弱ければ改善後の見出し構成を出す。

## 6. スマホでの読みやすさ  (中)

note はスマホ前提。

- 一文・一段落が長すぎないか。3〜4行程度で区切れているか。長い説明が塊になっていないか。
- 余白が足りているか。短すぎる1行段落が連続してリズムを崩していないか。
- 必要なら段落分割の修正例を出す。

## 7. 読まなくても読める設計  (中)

読者は読み飛ばす。視覚で意味が拾えるか。

- 太字にすべき箇所/太字が多すぎないか。キーワードを「」で囲むと分かりやすくならないか。
- 箇条書きにすべき箇所/図・スクショで説明した方が早い箇所。
- 見出し・太字・画像だけで概要が伝わるか。太字や「」の候補を具体的に示す。

## 8. 文体  (中)

整えすぎて筆者の声を消さない。**声の基準は対象記事の persona(`personas/<名前>.yaml`)**。汎用の良し悪しでなく
「その persona の声から外れていないか」で見る。

- 一文が長すぎないか。主語述語が対応しているか。指示語が曖昧でないか。漢字が多すぎないか。
- ひらがなにした方がやわらかい語。難語の使いすぎ。文末が単調でないか。
- 筆者らしい言い回しを削ろうとしていないか(persona の「好む書き方」「残した方がいい表現」を守る)。
- **AIっぽい言い回し(`ai-generic`)を狩る。** 何がクサい/canned か・温度の好みは **persona の「避ける言い回し」「判断の物差し」**に従う。
  狩る手順は次のとおり(機構): ①段取りの宣言 ②中身のない定型句 ③温度のない均質な説明調 ④経験を一般現在で書く決めつけ
  ——の4類型を疑い、persona の基準に照らして該当を **修正前/修正後/意図** で出す。具体の禁止語・時制スタンス・気取りの判定は persona を参照。
- 直すときは必ず**「修正前 / 修正後 / 意図」**で出す。整えすぎない(persona の「残した方がいい表現」とセットで判断)。

## 9. noteらしさ  (中)

情報だけでなく「その人が書いた意味」が要る。**基準は persona の「noteらしさ」「温度・距離」**。

- 筆者自身の体験・違和感・発見・迷いがあるか。ただの解説記事になっていないか。
- 読者との距離が近すぎ/遠すぎないか(persona の「温度・距離」に照らす)。個人的な話と一般化のバランス。余白・寄り道が適度か。
- 必要なら「ここに体験を足すとよい」場所を指摘する。

## 10. 画像・見出し画像  (中〜軽)

- 見出し画像が内容とズレていないか。OGP として見て内容が想像できるか。
- 画像・図を挟むべき箇所。スクショ/図解で分かりやすくなる箇所。装飾でなく理解を助けているか。
- 図の prompt で、技術名(ツール名)にそれと分かるアイコンが指定されているか(無地ラベルは識別しづらい。
  詳細は image-styles.md)。
- 画風・テンプレ顔回避・1セクション1図の厳格さ等の好みは **persona の `画像審美` / `編集観点.画像`** を見て
  判断する(無色なら指摘しない)。
- 必要なら画像生成プロンプト案も出す(note-figures に渡せる粒度)。

## 11. 公開前チェック  (重大〜軽が混在)

- 誤字脱字・表記ゆれ・主語抜け・指示語の曖昧さ・固有名詞。
- **前提・道具一覧の網羅性**(`reader-mismatch`): 「登場する道具」「前提環境」が、本文で実際に使う固有名詞
  ツールを**漏れなく**カバーしているか突合する。本文に出てくるのに一覧に無い裏方ツール(例: mise の
  ようなタスクランナー)は読者を置いていく。本文で使う固有名詞を洗い出し、一覧と機械的に照合すること。
- タイトルと本文の約束の一致・過度な断定・誤解されそうな表現。
- 引用や出典が必要な箇所(出典は note-writing の `<!-- cite: ... -->` 規約。note-spec.md 参照)。
- まとめが弱くないか。
- **note 仕様違反**(`spec-violation`)は note-spec.md を基準に判定: インラインコード `` `code` `` は不可、
  見出しは H2/H3 のみ、表はネイティブ非対応(画像化)、数式は `$$`、等。
